Docker Compose “variable is not set. Defaulting to a blank string”: fail CI instead

Compose treats an unset ${VAR} as a warning, substitutes an empty string, and keeps going. Here is how to make that a CI failure, and how to keep .env.example in step with compose.yaml.

You run docker compose up or docker compose config and see a line like this:

level=warning msg="The \"DATABASE_URL\" variable is not set. Defaulting to a blank string."

The command still succeeds. The container starts with DATABASE_URL set to an empty string, and the failure shows up later as a connection error inside the app, not as a failed step. In CI the warning scrolls past in the log, and the job stays green.

Every command and output on this page was run on November 17, 2026 against a small sample project, with the standalone Docker Compose binary v2.40.3 (docker-compose version printed Docker Compose version v2.40.3), Node.js 24, and EnvGate 0.2.1. Only docker compose config was used; no containers were started. The timestamps in the output are from that run.

The sample project

compose.yaml uses every common way of pulling a value from the host:

services:
  web:
    image: "nginx:${NGINX_TAG:-1.27}"
    environment:
      DATABASE_URL: ${DATABASE_URL}
      REDIS_URL: ${REDIS_URL:?REDIS_URL must be set}
      WEBHOOK_SECRET:
      LOG_LEVEL: info
      SENTRY_DSN: ${SENTRY_DSN:-}

The committed .env.example only lists one of them:

DATABASE_URL=

What Compose does with each form

The Compose interpolation docs define the syntax: ${VAR} substitutes the value, ${VAR:-default} and ${VAR-default} fall back to a default, and ${VAR:?error} and ${VAR?error} “exit with error” when the variable is missing. The docs also say that if a variable is not set, Compose substitutes an empty string. Values come from your shell, then a file passed with --env-file, then (if --env-file is not used) a .env file in the project directory.

With nothing set in the shell and no .env file:

$ docker compose config > /dev/null; echo "exit=$?"
time="2026-11-17T17:18:08-05:00" level=warning msg="The \"DATABASE_URL\" variable is not set. Defaulting to a blank string."
error while interpolating services.web.environment.REDIS_URL: required variable REDIS_URL is missing a value: REDIS_URL must be set
exit=1

Only the :? form failed the command. With REDIS_URL set, the exit code drops to 0 and the rendered config shows what the container would actually get:

$ REDIS_URL=redis://cache:6379 docker compose config; echo "exit=$?"
time="2026-11-17T17:18:15-05:00" level=warning msg="The \"DATABASE_URL\" variable is not set. Defaulting to a blank string."
name: cdemo
services:
  web:
    environment:
      DATABASE_URL: ""
      LOG_LEVEL: info
      REDIS_URL: redis://cache:6379
      SENTRY_DSN: ""
      WEBHOOK_SECRET: null
    image: nginx:1.27
    networks:
      default: null
networks:
  default:
    name: cdemo_default
exit=0

Three things to notice:

  • ${DATABASE_URL} produced a warning and an empty string, with exit code 0.
  • WEBHOOK_SECRET: with no value is a pass-through from the host. It was unset, and Compose printed no warning at all; the rendered value is null.
  • ${SENTRY_DSN:-} and ${NGINX_TAG:-1.27} are explicitly optional. No warning, by design.

Adding a .env file next to compose.yaml containing DATABASE_URL=postgres://app@db/app made the warning go away and the rendered value became postgres://app@db/app. That is the usual reason the warning appears in CI but not locally: the developer has a .env, and the runner does not.

Fix 1: mark required variables with :?

The cheapest fix lives in compose.yaml itself. Change ${DATABASE_URL} to ${DATABASE_URL:?DATABASE_URL must be set} for anything the service cannot run without. As shown above, Compose then refuses to render the config and exits 1, both locally and in CI.

Two limits. :? only covers ${...} interpolation, not the pass-through form (WEBHOOK_SECRET: or - WEBHOOK_SECRET). And it is opt-in per variable, so a new ${VAR} added without it goes back to warning-only.

Fix 2: turn the warning into a failing CI step

docker compose config --help in v2.40.3 lists no option that makes this warning fatal, so capture stderr and check it. The step below was tested under bash -e; GitHub Actions bash steps also run with -e:

      - name: Fail on unset Compose variables
        shell: bash
        run: |
          status=0
          docker compose config --quiet 2> compose-warnings.txt || status=$?
          cat compose-warnings.txt >&2
          if grep -q "variable is not set" compose-warnings.txt; then status=1; fi
          exit $status

Results against the sample project:

nothing set                                  exit=1  (warning + REDIS_URL error)
REDIS_URL set                                exit=1  (DATABASE_URL warning)
DATABASE_URL and REDIS_URL set               exit=0
DATABASE_URL set but empty, REDIS_URL set    exit=0

The || status=$? matters: without it, bash -e exits as soon as docker compose config fails, before the captured error is printed, and the log shows a failed step with no reason. The last row is the gap in this approach: a variable that is set to an empty string — for example a GitHub Actions secret that does not exist, which expands to "" — does not trigger the warning. The unset pass-through WEBHOOK_SECRET did not trigger it either.

Fix 3: check the required keys before Compose runs

The free EnvGate Lite GitHub Action reads key names from .env.example and fails the job if any are unset in the job environment, or empty when fail-on-empty is on. Set the variables at the job level so the check and the Compose step see the same values:

jobs:
  compose-check:
    runs-on: ubuntu-latest
    env:
      DATABASE_URL: ${{ secrets.DATABASE_URL }}
      REDIS_URL: ${{ secrets.REDIS_URL }}
      WEBHOOK_SECRET: ${{ secrets.WEBHOOK_SECRET }}
    steps:
      - uses: actions/checkout@v5
      - uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"
      - run: docker compose config --quiet

Run locally through the action’s own entry point, with .env.example listing all three keys, REDIS_URL set, WEBHOOK_SECRET set to an empty string, and DATABASE_URL unset, it printed:

::error title=Missing env key::DATABASE_URL is listed in .env.example but is not set
::error title=Empty env key::WEBHOOK_SECRET is set but empty
EnvGate Lite: 1 missing, 1 empty (of 3).

and returned exit code 1. With all three set to non-empty values it printed EnvGate Lite: OK, 3 key(s) present. and returned 0. Unlike the stderr check, this catches the empty-string case and the pass-through key. Its limit is the other direction: Lite only knows the keys that are in .env.example. In the original sample, where the example listed only DATABASE_URL, Lite would never ask about REDIS_URL or WEBHOOK_SECRET.

Keep .env.example in sync with compose.yaml

That leaves the drift itself: someone adds ${REDIS_URL} to compose.yaml and never adds it to .env.example. The EnvGate CLI reads Compose files in scan mode and reports interpolated or pass-through keys that are not listed in a nearby example file. Against the original sample:

$ envgate check
EnvGate check
  examples: .env.example
  env:      (none)
  compose:  compose.yaml

Warnings (2):
  [compose_undocumented] REDIS_URL: Compose key "REDIS_URL" in compose.yaml is interpolated or passed through from the host, but is not listed in a nearby example file.
  [compose_undocumented] WEBHOOK_SECRET: Compose key "WEBHOOK_SECRET" in compose.yaml is interpolated or passed through from the host, but is not listed in a nearby example file.

PASS — no violations.
(2 warnings)
$ echo $?
0

It skipped DATABASE_URL (documented), LOG_LEVEL (a literal value in the Compose file), and the :- defaults. These are warnings, so the exit code is 0. To make them fail CI, use the JSON report:

$ envgate check --json | jq -e '.summary.compose == 0'
false
$ echo $?
1

After adding REDIS_URL= and WEBHOOK_SECRET= to .env.example, envgate check printed PASS — no violations. with no warnings, and the jq check printed true and exited 0. At that point the Lite Action step above covers all three keys.

Limits worth knowing

  • The stderr check matches Compose’s current warning text. If a future Compose release rewords it, the grep needs updating.
  • EnvGate’s Compose reader is line-based and is not a full YAML parser. It ignores COMPOSE_* and DOCKER_* names, and treats $$ as a literal dollar, as Compose does.
  • None of these checks tell you a value is correct. A set, non-empty DATABASE_URL pointing at the wrong host passes all three.
  • Values are never printed by EnvGate or EnvGate Lite; only key names. docker compose config without --quiet does print resolved values, so avoid it in CI logs when real secrets are set.
