Prevent Node.js deploys from failing on missing environment variables

Three layers of defense: fail fast at startup, check before deploy, and keep the list of required variables in one place.

“It worked on my machine” is very often an environment variable. A Node.js app reads process.env.SOMETHING, gets undefined in production, and fails somewhere far from the actual cause: a database client that can’t parse its connection string, a payment SDK throwing on an empty key, or a URL that literally contains the text undefined. This guide covers three layers of defense: fail fast at startup, check before deploy, and keep the list of required variables in one place.

Why missing variables fail late

process.env is a plain object of strings. Reading a key that isn’t there returns undefined, and nothing complains. If the read happens lazily, say inside the first request handler that sends an email, the app boots, passes its health check, and only breaks when that code path runs. Some coercions make it worse: Number(undefined) is NaN, and template strings turn undefined into the literal text "undefined".

Layer 1: validate configuration at startup

Read every variable once, in one module, when the process starts, and exit with a clear message if anything required is missing. Everything else imports from this module instead of touching process.env directly:

// config.js
const required = ['DATABASE_URL', 'SESSION_SECRET', 'STRIPE_SECRET_KEY'];

const missing = required.filter(
  (key) => process.env[key] === undefined || process.env[key].trim() === ''
);

if (missing.length > 0) {
  // Names only - never log values.
  console.error(`Missing required environment variables: ${missing.join(', ')}`);
  process.exit(1);
}

const port = Number.parseInt(process.env.PORT ?? '3000', 10);
if (!Number.isInteger(port) || port <= 0) {
  console.error('PORT must be a positive integer');
  process.exit(1);
}

module.exports = Object.freeze({
  databaseUrl: process.env.DATABASE_URL,
  sessionSecret: process.env.SESSION_SECRET,
  stripeSecretKey: process.env.STRIPE_SECRET_KEY,
  port,
});

Require ./config at the very top of your entry file. Now a missing variable stops the process immediately, and most platforms will mark the release as failed rather than routing traffic to a half-working app. Schema libraries (zod, envalid, and others) can do the same with type coercion if you want more than presence checks.

Loading .env files in modern Node.js

Recent Node.js versions can load a .env file without any package. node --env-file=.env app.js has been available since Node 20.6, and process.loadEnvFile() since Node 20.12 and 21.7. If a variable is already set in the real environment, that value wins over the file, which is what you want on servers where the platform injects configuration. The popular dotenv package behaves the same way by default: it doesn’t override existing variables unless you pass override: true.

Either way, a loader only loads. It won’t tell you that the file is missing a key the code needs. That’s why the startup check above still matters.

Layer 2: check before you deploy

Startup validation catches the problem when the new release boots, which is late. If the deploy pipeline can check the configuration before shipping, a missing variable never reaches production at all. The question to ask is: does the target environment define every key the code expects?

That needs a list of expected keys, which brings us to .env.example.

Layer 3: one list of required keys

The required array in config.js, the keys in .env.example, and the variables wired into CI are three copies of the same list, and they drift. Pick one source of truth. A practical choice is .env.example, because it’s already committed and humans already read it. You can derive the startup list from it at build time, or simply have CI verify that the deploy environment matches it:

# In CI, before the deploy step (GitHub Actions)
- name: Check deploy env against .env.example
  uses: ESS2292/envgate-action@v1
  with:
    fail-on-empty: "true"
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
    SESSION_SECRET: ${{ secrets.SESSION_SECRET }}
    STRIPE_SECRET_KEY: ${{ secrets.STRIPE_SECRET_KEY }}

That step uses the free EnvGate Lite action, which reads the key names from .env.example and fails the job if any isn’t set. On platforms that inject configuration from a dashboard rather than from CI (many PaaS hosts work this way), add a pre-deploy step that exports the platform’s variable names, if its CLI supports that, and compares them to the example.

A checklist for deploy-safe configuration

  • Every variable is read in one config module, at startup.
  • Required variables cause a non-zero exit, with the key name in the message and no values.
  • .env.example lists every key, with empty or obviously fake values.
  • Pull requests that add a new process.env read also update .env.example (worth adding to your PR template).
  • CI verifies the deploy environment against .env.example before shipping.
  • Nobody logs process.env wholesale, even when debugging.

Where EnvGate fits

Missing keys are the most common configuration failure, but not the only one. Values copied straight from the example (your_api_key_here, CHANGEME, empty strings) are present and still wrong, and a real token pasted into the wrong file is its own problem.
