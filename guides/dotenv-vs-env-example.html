dotenv vs .env.example: keeping config in sync

One file holds values, the other holds the contract. Here's how to stop them drifting apart.

If you’ve used dotenv, you’ve probably seen both a .env and a .env.example in the same repository. They look almost identical, which makes it easy to miss that they do completely different jobs. This guide explains the split, how the two files drift apart, and a few low-effort ways to keep them in sync.

What dotenv actually does

dotenv is a loader. At startup it reads .env and copies each KEY=VALUE pair into process.env:

// index.js
require('dotenv').config(); // reads .env from the current working directory

console.log(process.env.APP_NAME ? 'config loaded' : 'APP_NAME not set');

That’s all it does. By default it won’t override variables that are already set in the real environment, and it doesn’t know or care which keys your app needs. A missing .env file, or one missing half its keys, isn’t an error to dotenv. (Recent versions of Node.js can also load env files natively with node --env-file=.env; the same point applies.)

What .env.example is for

.env.example isn’t read by any library by default. It’s documentation: a committed, secret-free list of every variable the app expects, ideally with comments.

# .env.example — copy to .env and fill in real values
APP_NAME=my-app
PORT=3000

# Postgres connection string
DATABASE_URL=

# From the Stripe dashboard (test key for local dev)
STRIPE_SECRET_KEY=

So the split is: .env holds values (often secret, never committed, different on every machine), and .env.example holds the contract (key names, safe defaults, committed). The usual .gitignore entry is:

.env
.env.*
!.env.example

How they drift

The contract is only as good as the discipline behind it. Drift happens in predictable ways:

  • New key, no example update. A developer adds process.env.REDIS_URL, sets it in their own .env, and forgets the example. Everyone else’s app breaks on pull.
  • Example updated, nobody’s .env is. The example is right, but existing .env files don’t update themselves. People find out from a stack trace.
  • Renamed keys. DB_URL becomes DATABASE_URL. Old files keep the old name, which now does nothing, and the new key is missing.
  • Placeholders that never got replaced. cp .env.example .env is a common setup step, so values like your_api_key_here end up in real .env files.

Ways to keep them in sync

1. Make the check part of startup

dotenv-safe is a long-standing package that wraps dotenv and throws if any variable listed in .env.example isn’t defined. If you’re happy adding a dependency to your runtime, it’s a direct fix for the “example updated, .env isn’t” case. Alternatively, a few lines of your own code can compare the two files; the validation guide has a dependency-free script.

2. Add a pre-commit or pre-push hook

Running the comparison in a git hook catches drift on the developer’s machine. It won’t catch a key that was added to the code without being added to either file, but it will catch the far more common case of a stale local .env:

#!/bin/sh
# .git/hooks/pre-push  (make it executable: chmod +x .git/hooks/pre-push)
node check-env.js .env .env.example || {
  echo "Your .env is out of sync with .env.example (see above)."
  exit 1
}

3. Check CI against the example

CI is where drift is cheapest to catch for everyone, because it runs on every push. The free EnvGate Lite GitHub Action reads the keys from .env.example and fails the job if any isn’t set in the job’s environment or in an env file you point it at. When someone adds a key to the example without wiring the matching secret into CI, the run fails on that step and names the key.

4. Review it like code

A line in your pull-request template, “If this PR reads a new environment variable, it’s in .env.example with a comment,” costs nothing and catches the case no tool can: a variable read in code but missing from every file.

What not to put in .env.example

  • Real credentials, even “test” ones that work. The file is committed and often public.
  • Values that look real. A fake key that matches a real provider’s format can trip secret scanners and confuse people. Leave it empty or write something obviously fake.
  • Production-only defaults that would be dangerous if copied to a laptop, such as a production database host.

Summary

dotenv loads values; .env.example documents the contract. Nothing connects them unless you add a check, at startup, in a git hook, in CI, or all three.
