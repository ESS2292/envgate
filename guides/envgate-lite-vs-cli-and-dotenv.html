EnvGate Lite vs the CLI, dotenv, and schema validators

Load, validate, and gate are different jobs. Here is what each tool actually does, and when to use more than one.

Several good tools overlap here, and they are not competitors in a zero-sum way. dotenv loads values. dotenv-safe loads and then requires every key from .env.example. Schema validators like zod or envalid type-check config at startup. EnvGate Lite and the EnvGate CLI do not load files into process.env; they check that required keys are actually set, and they never print values.

Use this page to pick the right check, or to combine them. A loader plus a schema check plus a CI gate is a solid setup, not overkill.

When to use each

dotenv

dotenv (and Node’s node --env-file) only loads. It will not error if the file is missing, or if a key your app needs is absent. A loader also will not override a variable that is already set in the real environment, unless you pass override: true. Keep using it to load values; just don’t expect it to validate them.

dotenv-safe

If you already use dotenv and want a startup failure when .env is missing a key from .env.example, dotenv-safe is a well-known, dependency-based fix. It is a good choice when you want the check inside the running app. Confirm how it treats empty values in the version you use; an empty DATABASE_URL= is not the same as a missing key.

envalid, zod, and similar schemas

A schema at startup is the strongest way to fail fast in the app itself: missing keys, wrong types, and empty strings can all become a named boot error. EnvGate does not replace that. --schema is not implemented in the current EnvGate CLI. If you want typed validation, keep zod or envalid (or pydantic, in Python) at process start, and use EnvGate for the file-and-CI layer.

EnvGate Lite

The free EnvGate Lite GitHub Action answers one question in CI: is every key listed in .env.example set, either in a file you point it at or in the job’s environment? Use it when you want a required-key gate on GitHub Actions without adding a runtime dependency. Turn fail-on-empty on, because a missing repository secret arrives as an empty string, not as an unset variable.

It does not detect placeholders, extra keys, or secret shapes, and it is not a local CLI.

EnvGate CLI

The $19 CLI is for people who want the same check on a laptop, in a pre-commit hook, or in any CI system, plus the extras Lite leaves out: placeholder and empty values, extra-key warnings (or errors with --strict-extra), a focused secret-shape detector, and a JSON report. Values stay redacted. Parsing does not include multiline values or $VAR or ${VAR} expansion, and the secret-shape list is deliberately narrow — it is not a replacement for a dedicated secrets scanner.

A practical combination

  1. Keep a committed .env.example as the contract (key names and safe defaults, never real secrets).
  2. Load values with dotenv or node --env-file.
  3. Validate types and required values at startup with a schema library if your app is non-trivial.
  4. In GitHub Actions, add EnvGate Lite with fail-on-empty: "true" so a forgotten repo secret fails the job before deploy.
  5. If you also want placeholder, extra-key, and secret-shape checks locally or in other CI, use the EnvGate CLI.

Summary

Load, validate, and gate are different jobs. dotenv loads. dotenv-safe and schema libraries validate at startup. EnvGate Lite gates GitHub Actions against .env.example. The EnvGate CLI extends that check to your machine and adds placeholder, extra-key, and narrow secret-shape findings, without printing values.

Want more than a missing-key check?

The free EnvGate Lite GitHub Action fails a CI job when a key from .env.example isn’t set.
