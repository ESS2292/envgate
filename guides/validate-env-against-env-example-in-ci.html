Validate .env against .env.example in CI

CI usually has no committed .env. Map secrets into the job or write a temporary file, then fail the pipeline when a required key is missing or empty.

Validating a .env file against .env.example is straightforward on a laptop: both files are in the working tree, and a script can compare key names before you start the app. CI is different. You usually should not have a committed .env with real values. Secrets arrive as the runner’s environment variables, or you write a temporary file from those variables and hand it to a deploy tool. The check still answers the same questions — is every required key present, and is any of them empty? — but the way you feed it data changes.

This guide covers those CI patterns. For a shell one-liner or a small Node.js script you can also run locally, see How to validate a .env file against .env.example.

What to check, and what to print

In CI, a useful validator should:

  • Take the required key names from a committed .env.example (the contract), not from a hard-coded list in the workflow that will drift.
  • Fail the job with a non-zero exit code when a required key is missing or empty, so later steps do not run.
  • Print key names only. CI logs are often readable by more people than the secrets are. Never echo values, even on failure.

A presence-only check is not enough. In GitHub Actions, a missing secret expands to an empty string; in any CI, a generated file can contain API_KEY= or a placeholder copied from the example. Treat empty values as failures for required keys. The details of the GitHub Actions empty-secret case are in GitHub Actions secret is empty: why and how to fail fast.

Pattern 1: check the job environment

This is the natural fit when the app or deploy step reads environment variables rather than a file. You map secrets and variables into the job, then check that every key in .env.example is set and non-empty there.

On GitHub Actions, the free EnvGate Lite action does exactly that. It also never prints values:

      - uses: actions/checkout@v5
      - name: Check required env vars
        uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          API_KEY: ${{ secrets.API_KEY }}
          APP_NAME: ${{ vars.APP_NAME }}

A key counts as present if it is in the job environment. You do not need a .env file on the runner for this pattern.

Pattern 2: write a file, then validate the file

Some deploy tools want a file such as .env.production. Build that file from CI secrets, then validate it against .env.example before you deploy. The same action can check a file; a key still counts as present if it is in the file or in the job environment:

      - name: Write .env for deploy
        run: |
          echo "DATABASE_URL=${{ secrets.DATABASE_URL }}" >> .env.production
          echo "API_KEY=${{ secrets.API_KEY }}" >> .env.production
          echo "APP_NAME=${{ vars.APP_NAME }}" >> .env.production

      - name: Check .env.production against .env.example
        uses: ESS2292/envgate-action@v1
        with:
          env-file: .env.production
          fail-on-empty: "true"

Two cautions. First, writing echo "KEY=${{ secrets.KEY }}" will still write an empty value when the secret is missing, which is why fail-on-empty matters. Second, do not cat the file in the logs, and do not upload it as an artifact.

Other CI systems

The same two patterns work anywhere you can run Node.js or a shell and fail the job on a non-zero exit code. In GitLab CI, for example, you can write a temporary file from CI variables and run a small checker:

# .gitlab-ci.yml (sketch)
validate-env:
  image: node:22
  script:
    - |
      printf '%s\n' "DATABASE_URL=${DATABASE_URL}" "API_KEY=${API_KEY}" "APP_NAME=${APP_NAME}" > .env.ci
    - node check-env.js .env.ci .env.example
    # do not cat .env.ci

check-env.js can be the dependency-free script from the local validation guide: it exits 1 when a key is missing or empty and prints names only. Keep that script in the repository so the runner does not have to download it. The EnvGate CLI can be used the same way in any CI that has Node.js 18+ once you have the package unpacked on the runner; it also flags placeholders, extra keys, and a narrow set of secret shapes, with values redacted, and it can emit --json.

The important part is the exit code, not the brand of CI:

  • 0 — the check passed (some tools allow warnings without failing).
  • 1 — violations: missing, empty, or, if you opted in, other failures.
  • 2 — setup error, such as a missing .env.example (this is how the EnvGate CLI reports it).

Place the check before work that depends on the config

Run the validator as an early job or as the first step of the deploy job, before tests that need real credentials and before any deploy. If a required key is missing, there is no reason to build a container or push to a host. On GitHub Actions, skip this privileged check on fork pull requests, because those events do not receive repository secrets; see the empty-secrets guide for a job if: condition.

What not to do

  • Do not commit a real .env so that CI can read it. The example file is the contract; values belong in the runner’s secret store.
  • Do not print values in echo, cat, debug logs, or artifacts.
  • Do not treat a copied placeholder as success. API_KEY=your_api_key_here is present and non-empty. If people start from .env.example, you also need a placeholder check, which Lite does not do and the CLI does.
  • Do not assume the check scans the repo. A file-based validator only reads the paths you pass it. It will not find a secret that was committed in some other file.
