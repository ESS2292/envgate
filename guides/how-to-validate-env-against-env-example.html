How to validate a .env file against .env.example

Check for missing, empty, and extra keys with a one-liner, a small Node.js script, or a CLI, and get an exit code that CI and git hooks can act on.

Most projects that use a .env file also commit a .env.example: the same keys, with blank or fake values, so a new teammate (or a CI job, or a server) knows which variables the app expects. The trouble is that nothing keeps the two files in sync. Someone adds STRIPE_WEBHOOK_SECRET to the code and to .env.example, and every other copy of .env in the world is now quietly out of date.

Validating .env against .env.example means answering a few concrete questions, ideally automatically:

  • Missing keys: is every key from the example present in the real file?
  • Empty or placeholder values: is anything still blank, TODO, CHANGEME, or your_api_key_here?
  • Extra keys: are there keys in .env that the example doesn’t list? Those are often typos (DATABSE_URL) or leftovers nobody documented.

Below are three ways to do it, from a shell one-liner to a script you can drop into CI.

Option 1: a quick shell check

If you only care about missing keys, standard Unix tools are enough. This pulls the key names out of each file, sorts them, and prints keys that appear in the example but not in .env:

keys() { grep -E '^[[:space:]]*(export[[:space:]]+)?[A-Za-z_][A-Za-z0-9_]*=' "$1" \
  | sed -E 's/^[[:space:]]*(export[[:space:]]+)?//; s/=.*//' | sort -u; }

comm -23 <(keys .env.example) <(keys .env)

comm -23 prints lines only in the first input; both inputs must be sorted, which is why keys ends with sort -u. Swap to comm -13 to list extra keys instead. This is fine for a quick look, but it doesn’t set a useful exit code, ignores empty values, and needs bash for the <( ) process substitution.

Option 2: a small Node.js script

A script gives you a proper exit code, which is what CI and git hooks care about. This one has no dependencies and runs on any current Node.js version:

// check-env.js — usage: node check-env.js [.env] [.env.example]
const fs = require('node:fs');

function parse(file) {
  const out = new Map();
  for (let line of fs.readFileSync(file, 'utf8').split(/\r?\n/)) {
    line = line.trim().replace(/^export\s+/, '');
    if (!line || line.startsWith('#')) continue;
    const eq = line.indexOf('=');
    if (eq <= 0) continue;
    out.set(line.slice(0, eq).trim(), line.slice(eq + 1).trim());
  }
  return out;
}

const [envPath = '.env', examplePath = '.env.example'] = process.argv.slice(2);
const env = parse(envPath);
const example = parse(examplePath);

const missing = [...example.keys()].filter((k) => !env.has(k));
const empty = [...example.keys()].filter((k) => env.has(k) && env.get(k) === '');
const extra = [...env.keys()].filter((k) => !example.has(k));

for (const k of missing) console.error(`missing: ${k}`);
for (const k of empty) console.error(`empty:   ${k}`);
for (const k of extra) console.warn(`extra:   ${k}`);

// Print key names only - never values.
process.exit(missing.length || empty.length ? 1 : 0);

Run it with node check-env.js. It exits 1 when a key is missing or empty and 0 otherwise; extra keys are warnings. Notice that it only ever prints key names. That matters: CI logs are often readable by more people than your secrets are, so a validator should never echo values.

The parser is intentionally minimal. It doesn’t strip quotes or inline comments, so KEY="" counts as non-empty. If your files use quoting, multiline values, or ${VAR} expansion, either keep them simple or use a tool with a real parser.

Option 3: run it automatically

A check only helps if it runs. Two good places:

  • Before the app starts. Add it to your start script, e.g. "prestart": "node check-env.js" in package.json, so a developer with a stale .env gets a clear message instead of a confusing runtime error.
  • In CI, before tests or deploy. In CI there often isn’t a .env file at all; secrets arrive as environment variables. Check those against the example too. The GitHub Actions guide covers that case.

Common pitfalls

  • Placeholder values pass a presence check. API_KEY=your_api_key_here is “present.” If people copy .env.example to .env as a starting point, you also need to flag known placeholder patterns.
  • Duplicate keys. Most loaders use one of the duplicates (which one depends on the loader). Your validator should agree with your loader, or at least warn.
  • Real values in the example. .env.example is committed, so it must never contain a real credential. Use empty values or obviously fake ones.
  • Silent drift in the other direction. If a key is removed from the code but left in .env.example, everyone keeps supplying a value nobody uses. Periodically compare the example against what the code actually reads.
