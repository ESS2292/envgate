Catch missing environment variables in GitHub Actions

Fail the job on its first step, with the missing key's name, instead of a confusing crash during deploy.

A missing environment variable in CI usually fails late and unclearly: the tests pass, the build passes, and then the deploy step or the app itself crashes with undefined somewhere in a stack trace. The fix is to check required variables up front, as the first step of the job, and fail with a message that names the missing key.

This guide covers how secrets and variables reach a GitHub Actions job, the cases where they silently go missing, and how to add a check that fails fast without leaking values into logs.

How configuration reaches a job

GitHub Actions has two stores for configuration: secrets (encrypted, masked in logs, read with ${{ secrets.NAME }}) and variables (plain text, read with ${{ vars.NAME }}). Both can be defined at the organization, repository, or environment level. Neither is exposed to your code automatically. You map them into environment variables yourself:

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    env:
      DATABASE_URL: ${{ secrets.DATABASE_URL }}
      API_KEY: ${{ secrets.API_KEY }}
      APP_NAME: ${{ vars.APP_NAME }}
    steps:
      - uses: actions/checkout@v5
      - run: npm ci && npm run deploy

Why variables go missing

  • The secret was never created. Referencing a secret that doesn’t exist doesn’t raise an error; the expression evaluates to an empty string. Your variable is set, but empty.
  • Someone added a key to the code but not to the workflow. The new key is in .env.example and in local .env files, but the env: block above was never updated, so it isn’t set at all.
  • The secret lives in an environment the job doesn’t use. Environment secrets are only available to jobs that declare that environment:.
  • Pull requests from forks. Workflows triggered by pull_request from a fork don’t receive your repository’s secrets (apart from a read-only GITHUB_TOKEN). Jobs that need secrets should skip cleanly in that case rather than fail mysteriously.

Because of the first point, a useful check has to distinguish not set from set but empty, and treat both as failures for required keys.

Option 1: a shell step

For a short list of keys, a bash step is enough. It uses indirect expansion to look each name up and prints names only:

      - name: Check required env vars
        shell: bash
        run: |
          status=0
          for key in DATABASE_URL API_KEY APP_NAME; do
            if [ -z "${!key:-}" ]; then
              echo "::error title=Missing env var::$key is not set or empty"
              status=1
            fi
          done
          exit $status

The ::error:: prefix is a workflow command: GitHub shows it as an annotation on the run summary. The downside is that the list of keys is now hard-coded in a second place, and it will drift from .env.example just like everything else.

Option 2: check against .env.example with the free action

Better: let .env.example be the single list of required keys and check the job against it. The free EnvGate Lite action does exactly that, with no dependencies:

      - uses: actions/checkout@v5

      - name: Check env against .env.example
        uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          API_KEY: ${{ secrets.API_KEY }}
          APP_NAME: ${{ vars.APP_NAME }}

It reads the key names from .env.example and fails the job if any is missing from the job’s environment, or from an env-file if you pass one (a key counts as present in either). With fail-on-empty on, it also catches secrets that were never created. Each problem key gets an annotation and a row in the job summary, and values are never printed. Now when someone adds a key to .env.example without wiring it into CI, the next run fails on the first step and names the key.

Keeping secrets out of logs

GitHub masks registered secret values in logs, but masking is a safety net, not a guarantee. Derived values (a secret that was base64-encoded, split, or embedded in JSON) may not match the mask. A few habits help:

  • Never echo a secret or run env/printenv in a step “to debug.”
  • Validators should report key names and problem types only, never values or partial values.
  • When you write secrets to a file for a deploy tool, write it with a heredoc or printf and don’t cat it afterward.
  • Use permissions: to give the job only what it needs.

Handling forks gracefully

Secrets can’t be referenced directly in an if: condition. A common pattern is to map the secret into a job-level env var and skip deploy-only steps when it’s empty:

    env:
      DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
    steps:
      - name: Deploy
        if: env.DEPLOY_TOKEN != ''
        run: ./deploy.sh

Keep the required-variables check on jobs that genuinely need secrets (deploys, integration tests) and leave it off jobs that run on untrusted fork PRs.
