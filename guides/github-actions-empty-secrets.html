GitHub Actions secret is empty: why and how to fail fast

A missing secret does not fail the workflow. It becomes an empty string. Check for that before deploy, and never print the value.

If you map a GitHub Actions secret into an environment variable and the secret does not exist, the job does not fail. The expression evaluates to an empty string. The variable is set, but empty. A later deploy step can look configured and still run with a blank credential, and the failure shows up in the app or the hosting provider rather than in the workflow.

This is different from a secret you forgot to map at all. That case leaves the variable unset. A check that only asks “is this key in the environment?” will pass the empty-string case, which is the one GitHub Actions gives you when a name is wrong or a secret was never created.

What GitHub Actions actually does

Secrets and variables are not injected into your process automatically. You map them yourself:

jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      DATABASE_URL: ${{ secrets.DATABASE_URL }}
      API_KEY: ${{ secrets.API_KEY }}
      APP_NAME: ${{ vars.APP_NAME }}
    steps:
      - uses: actions/checkout@v5
      - run: npm run deploy

If API_KEY is not defined as a repository, environment, or organization secret, ${{ secrets.API_KEY }} becomes "". In a shell, $API_KEY is set and has length zero. In Node.js, process.env.API_KEY is "" — falsy, but not undefined. The env: block still ran; nothing in the Actions UI reports a missing secret.

Why a secret arrives empty

  • The secret was never created, or it was created under a different name than the one in the workflow (APIKEY versus API_KEY).
  • It lives on a GitHub Environment such as production, and the job did not declare environment: production.
  • It is an organization secret that is not available to this repository.
  • The workflow is a pull_request from a fork. Fork PRs do not receive repository secrets, only a read-only GITHUB_TOKEN. The expressions still expand; they expand to empty strings.
  • The secret exists and is literally empty — uncommon, but a presence check would still treat it as set.

None of these are syntax errors. The workflow file is valid. That is why the job can get as far as tests or a deploy step before anything looks wrong.

Unset versus empty, and why it matters

A useful check has to treat both cases as failure for required keys:

  • Unset: you never mapped the key into the job (it is not in the env: block, and it is not otherwise in the process environment).
  • Empty: you mapped it, but the value is blank or only whitespace, including the missing-secret expansion above.

If you only test that a name is present, the second case slips through. If you only test a hard-coded list in a shell step and someone adds a key to .env.example and the app but not to that list, the first case slips through too. The list of required names should come from one place — usually a committed .env.example.

Fail fast with a shell step

For a short, stable list of keys, a bash step is enough. It uses indirect expansion so it can print names only:

      - name: Check required env vars
        shell: bash
        run: |
          status=0
          for key in DATABASE_URL API_KEY APP_NAME; do
            if [ -z "${!key+x}" ] || [ -z "${!key}" ]; then
              echo "$key is missing or empty" >&2
              status=1
            fi
          done
          exit $status

[ -z "${!key+x}" ] is true when the variable is unset; [ -z "${!key}" ] is true when it is unset or empty. Together they cover both cases. Do not echo the values. CI logs are often visible to more people than the secrets themselves, and a failed check should name the key, not the credential.

The drawback is the hard-coded list. It will drift from .env.example the same way workflow env: blocks already do.

Fail fast from .env.example

The free EnvGate Lite GitHub Action reads required key names from your .env.example and checks them against an env file you point it at, the job’s environment variables, or both. It never prints values. By default it fails only on missing keys; turn on fail-on-empty: "true" to catch the empty-secret case this guide is about:

      - uses: actions/checkout@v5
      - name: Check required env vars
        uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          API_KEY: ${{ secrets.API_KEY }}
          APP_NAME: ${{ vars.APP_NAME }}

A run against a file that was missing DATABASE_URL and had an empty API_KEY produced these annotations and a job summary that listed only the key names:

::error title=Missing env key::DATABASE_URL is listed in .env.example but is not set
::error title=Empty env key::API_KEY is set but empty
EnvGate Lite: 1 missing, 1 empty (of 3).

Put this step early in the job, before tests or deploy. The job fails with an exit code of 1, and the annotations name the problem keys. Outputs ok, missing, and empty are also available if a later step needs them.

Fork pull requests

Because fork PRs do not receive repository secrets, a fail-on-empty check on pull_request will fail for those events even when the workflow file is correct. Keep the check on jobs that are supposed to have secrets (for example push to your default branch, or pull requests from the same repository) and skip privileged jobs on fork PRs:

jobs:
  env-check:
    if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          API_KEY: ${{ secrets.API_KEY }}

What this check does not catch

An empty-or-missing check will not tell you that a value is a placeholder such as your_api_key_here or CHANGEME, that a typo created an extra key, or that a value looks like a live token in a file that should not contain one. Those are separate checks, and they belong in a local or CI tool that is built for them — not in a log line that prints the value.
