EnvGate / Guides

Guide · Updated November 10, 2026

Run EnvGate, RuntimeGate, and LockGate Lite in one workflow

Three free GitHub Actions, one job: fail on a missing env var, a drifted Node.js pin, or an unfrozen install, before the deploy step runs.

A CI job can pass tests and still ship a broken deploy. A secret was never created, so it arrives as an empty string. The Dockerfile still says Node 20, but setup-node moved to 22. The workflow runs npm install, so the tree on the runner is not the tree in the lockfile. Each of those is a different file, and each one is easy to miss on review.

The three free Lite Actions each watch one of those surfaces. You can run them in a single job, in any Actions workflow, with no paid download. This guide is the combined example.

  • EnvGate Lite fails when a key from .env.example is missing from the job environment (and, optionally, when it is present but empty).
  • RuntimeGate Lite fails when Node.js version pins in version files, package manifests, Dockerfiles, Compose, and setup-node steps disagree.
  • LockGate Lite fails when mixed lockfiles are committed, or when CI runs an unfrozen install instead of npm ci (or the Yarn / bun equivalent).

The workflow

Copy this into .github/workflows/ci-gates.yml. Change the env: names to the keys your .env.example actually lists. The DATABASE_URL and API_KEY lines below are examples, not a required set.

name: CI gates

on:
  pull_request:
  push:

jobs:
  gates:
    runs-on: ubuntu-latest
    env:
      DATABASE_URL: ${{ secrets.DATABASE_URL }}
      API_KEY: ${{ secrets.API_KEY }}
    steps:
      - uses: actions/checkout@v5

      - name: Check required environment variables
        uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"

      - name: Check runtime version pins
        uses: ESS2292/runtimegate-action@v1

      - name: Check lockfiles and CI installs
        uses: ESS2292/lockgate-action@v1

When a repository secret does not exist, ${{ secrets.DATABASE_URL }} expands to an empty string, so the variable is set but empty. fail-on-empty: "true" is what catches that case. EnvGate Lite reports key names only; it does not print values.

What each step needs

  • EnvGate Lite needs a template file, .env.example by default, and the required keys mapped into the job’s environment (or into an env-file). If the repository has no env template, omit this step rather than pointing it at a missing file.
  • RuntimeGate Lite scans the checkout for pins. It needs no extra inputs for the default check. Add eol: "true" if you also want the job to fail when a Node.js pin is past official end of support. The dates are vendored in the Action; there is no network call.
  • LockGate Lite also scans the checkout and needs no extra inputs for a typical app repository. If the project is a library that gitignores its lockfile (ESLint and Express do this), Lite treats that as an intentional policy: it warns instead of failing, and it does not flag npm install in CI, because a library that does not commit a lockfile cannot run npm ci. Set lockfile-policy: app if you still want a committed lockfile, or library to force the library policy without a gitignore. Manifests under tests/fixtures-style paths are skipped by default.

Where to put it in a larger pipeline

Run this job early, on the same push and pull_request events as the rest of CI, and make later jobs needs: gates if you want a failed gate to skip the build or deploy. On pull requests from forks, repository secrets are not available, so an EnvGate Lite step with fail-on-empty: "true" will fail if it expects those secrets. Keep the env check on jobs that are supposed to have secrets (for example push to the default branch, or pull requests from the same repository), and leave it off untrusted fork PRs.

What this workflow does not do

  • It does not install the paid CLIs, and it does not need a store checkout. The Lite Actions are the whole check.
  • EnvGate Lite does not flag placeholders, extra keys, or secret shapes; those are CLI-only.
  • RuntimeGate Lite does not, in this example, enable the end-of-life check unless you set eol: "true".
  • LockGate Lite does not compare package.json to package-lock.json and does not read Dockerfiles. Mixed lockfiles and unfrozen CI installs are what it covers here.

The three free Actions

Each Lite Action is MIT-licensed, has zero runtime dependencies, and runs on GitHub’s node24 JavaScript Action runtime.

  • EnvGate Lite — missing or empty keys from .env.example
  • RuntimeGate Lite — Node.js version pins that disagree
  • LockGate Lite — mixed lockfiles and unfrozen CI installs
