Python KeyError from os.environ in pytest on CI (the .env file is not loaded)

pytest does not read .env. Add load_dotenv(), pytest-dotenv, or pydantic-settings and the tests pass on your machine, but in CI the .env file is gitignored, so each of them quietly loads nothing. Then an empty GitHub secret gets past the KeyError entirely. Here is what each setup actually does, and how to make a missing or empty variable stop the run with a clear message.

The usual report: the job dies with ERROR collecting tests/... and KeyError: 'DATABASE_URL', or pydantic_core._pydantic_core.ValidationError: ... Field required, while the same tests pass locally.

Everything below was run on November 27, 2026 on Linux with Python 3.13.5, pytest 9.2.0, python-dotenv 1.2.4, pydantic-settings 2.16.3 (pydantic 2.14.4), pytest-dotenv 0.5.2, uv 0.13.9, Node.js 24.22.1 for EnvGate 0.2.1, and the EnvGate Lite Action source at tag v1 (commit aaae8a9). No GitHub Actions runner was used; where this page describes runner behavior, it quotes GitHub’s docs. Output is pasted as printed, except where a line says it was trimmed.

The error: pytest never reads .env

The sample project reads two required keys at import time and one optional key:

# app/config.py
import os

DATABASE_URL = os.environ["DATABASE_URL"]
JWT_SECRET = os.environ["JWT_SECRET"]
REDIS_URL = os.getenv("REDIS_URL")

A .env with all three keys sits next to pytest.ini. No loader, nothing exported in the shell:

$ pytest -q
==================================== ERRORS ====================================
____________________ ERROR collecting tests/test_config.py _____________________
tests/test_config.py:1: in <module>
    from app import config
app/config.py:3: in <module>
    DATABASE_URL = os.environ["DATABASE_URL"]
                   ^^^^^^^^^^^^^^^^^^^^^^^^^^
<frozen os>:717: in __getitem__
    ???
E   KeyError: 'DATABASE_URL'
=========================== short test summary info ============================
ERROR tests/test_config.py - KeyError: 'DATABASE_URL'
!!!!!!!!!!!!!!!!!!!! Interrupted: 1 error during collection !!!!!!!!!!!!!!!!!!!!
1 error in 0.04s
exit=2

The .env file was right there and pytest ignored it. Because the lookup runs at import time, it fails during collection, before any test runs, and pytest exits 2 (“Interrupted”), not 1. os.environ is a plain mapping of the process environment, so a missing key raises KeyError. os.getenv does not: the Python docs (cpython Doc/library/os.rst at v3.13.5, 6cb20a2) say it returns “the value of the environment variable key as a string if it exists, or default if it doesn’t”, and the default is None. With REDIS_URL unset, config.REDIS_URL printed REDIS_URL = None with no error, so that failure shows up later, wherever the value is first used.

The common loaders, and what they do in CI

Each of these fixed the local run (the test passed with the .env above). Then the .env file was removed, which is what a clean CI checkout looks like when .env is in .gitignore:

LoaderLocal, .env presentCI, no .env
load_dotenv() in conftest.pypass (returned True)returned False, no warning; same KeyError: 'DATABASE_URL' during collection, exit 2
pytest-dotenv with env_files = .env in pytest.inipassno warning; same KeyError, exit 2
pydantic-settings BaseSettings with env_file=".env"passno warning about the file; ValidationError: 2 validation errors for Settings … Field required [type=missing, ...], exit 1
uv run --env-file .env pytestpasserror: No environment file found at: .env, exit 2, before pytest starts

The python-dotenv source at v1.2.4 (a565c2c, src/dotenv/main.py) documents the return value as “True if at least one environment variable is set else False”. Its verbose option is described as “Whether to output a warning the .env file is missing”, but in that version the missing-file message is logged at INFO level, so load_dotenv('.env', verbose=True) with no file printed nothing here (it just returned False) unless logging is configured to show INFO.

pydantic-settings fails loudly, which is good, but for the wrong reason in CI: the message says the field is required, not that the job never set it. The uv run --env-file error is the only loader failure that names the file, and it fails even when the job sets every variable correctly, because the file is missing.

So all of these work the same way: when .env is there they fill the environment, and when it is not they do nothing (or, with uv --env-file, fail on the file). In CI the values have to come from the job’s environment.

The empty-variable trap: "" is not a KeyError

An environment variable set to an empty string exists, so os.environ["JWT_SECRET"] returns '' and nothing raises. And the loaders do not replace it. The python-dotenv README (1.2.4) says load_dotenv() will “Not override existing environment variables (override=False)”. The pydantic-settings docs (docs/index.md at v2.16.3, 50e676c): “environment variables will always take priority over values loaded from a dotenv file”, and “By default environment variables are parsed verbatim, including if the value is empty.”

Tested with a complete .env present (for the pytest run, a second test prints both values):

# conftest.py: load_dotenv()
$ DATABASE_URL= JWT_SECRET= pytest -q -s
load_dotenv() returned True
DATABASE_URL = '' JWT_SECRET = ''
(progress dots and traceback trimmed)
FAILED tests/test_config.py::test_database_url - AssertionError: assert False
1 failed, 1 passed in 0.01s
exit=1

# pydantic-settings, env_file=".env", plain str fields
$ JWT_SECRET= python ps/settings.py
database_url = 'postgres://app@localhost/app' jwt_secret = ''
exit=0

The loader returned True and still left both values empty. pydantic-settings accepted an empty jwt_secret as a valid str, with or without a .env file.

This matters in GitHub Actions because of how secrets expand. GitHub’s secrets docs (github/docs at 73e24e6): “If a secret has not been set, the return value of an expression referencing the secret … will be an empty string.” The same page: “With the exception of GITHUB_TOKEN, secrets are not passed to the runner when a workflow is triggered from a forked repository.” A line like JWT_SECRET: ${{ secrets.JWT_SECRET }} therefore sets JWT_SECRET to "" on fork pull requests or when the secret is misnamed, and your tests run with an empty key instead of failing on it. (The runner behavior is quoted from the docs; the precedence was tested locally as shown.)

Fix 1: a conftest.py that stops pytest before collection

Keep load_dotenv for local runs, and check every key that .env.example lists in pytest_configure, which runs before collection. Put this conftest.py in the repo root:

# conftest.py (repo root): fail before collection if a key from .env.example is unset or blank.
import os
from pathlib import Path

import pytest
from dotenv import load_dotenv

ROOT = Path(__file__).parent
load_dotenv(ROOT / ".env")  # local runs; does nothing if .env is absent


def pytest_configure(config):
    keys = []
    for line in (ROOT / ".env.example").read_text().splitlines():
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        line = line.removeprefix("export ").strip()
        keys.append(line.split("=", 1)[0].strip())
    missing = [k for k in keys if not os.environ.get(k, "").strip()]
    if missing:
        raise pytest.UsageError(
            f"Missing test env: {', '.join(missing)} (listed in .env.example)"
        )

.env.example lists DATABASE_URL, JWT_SECRET, and REDIS_URL. With no .env, DATABASE_URL set, JWT_SECRET set to an empty string, and REDIS_URL unset:

$ pytest -q
ERROR: Missing test env: JWT_SECRET, REDIS_URL (listed in .env.example)

exit=4

Other cases: all three keys set in the environment, 1 passed, exit 0; a complete local .env and nothing in the shell, exit 0; a complete .env plus JWT_SECRET= in the shell, exit 4 with Missing test env: JWT_SECRET (the empty-variable trap, now caught); JWT_SECRET set to spaces, also exit 4. Exit 4 is pytest’s documented code for a “pytest command line usage error” (pytest doc/en/reference/exit-codes.rst at 9.2.0, ae1d0ff), so CI treats it as a failure.

Two details that came from testing. The first version used Path(".env.example"), and running pytest from the tests/ directory crashed with INTERNALERROR … FileNotFoundError: [Errno 2] No such file or directory: '.env.example' (exit 3); anchoring both paths to Path(__file__).parent fixed that, and the same checks passed from tests/. And the parser is deliberately simple: it does not handle quoted keys or other unusual .env.example syntax beyond trimming and export.

Fix 2 (pydantic-settings): reject empty values in the model

If your config already lives in BaseSettings, make empty strings invalid there:

from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env")

    database_url: str = Field(min_length=1)
    jwt_secret: str = Field(min_length=1)
    redis_url: str = "redis://localhost:6379/0"
$ JWT_SECRET= python ps/settings_strict.py
(traceback trimmed)
pydantic_core._pydantic_core.ValidationError: 1 validation error for Settings
jwt_secret
  String should have at least 1 character [type=string_too_short, input_value='', input_type=str]
    For further information visit https://errors.pydantic.dev/2.14/v/string_too_short
exit=1

The other option in the docs, env_ignore_empty=True, treats an empty variable as unset. In a clean checkout that turned JWT_SECRET= into Field required [type=missing, ...], exit 1. But with a .env present it fell back to the file’s value and passed, so it hides an empty job variable on any machine that has a .env. Neither option caught JWT_SECRET set to spaces: min_length=1 plus env_ignore_empty=True printed ok for JWT_SECRET=' '.

Fix 3: check the job environment before installing anything

In GitHub Actions, put the values at job level so the check and the test step see the same environment, then run the free EnvGate Lite Action first:

jobs:
  test:
    runs-on: ubuntu-latest
    env:
      DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}
      JWT_SECRET: ${{ secrets.JWT_SECRET }}
      REDIS_URL: ${{ vars.REDIS_URL }}
      SENTRY_DSN: ${{ secrets.SENTRY_DSN }}
    steps:
      - uses: actions/checkout@v5
      - uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"
      - uses: actions/setup-python@v6
        with:
          python-version: "3.13"
      - run: pip install pytest python-dotenv
      - run: pytest

Run locally through the action’s own run() entry point at v1, with the action inputs passed as INPUT_* variables the way the runner does, DATABASE_URL set, JWT_SECRET empty, and REDIS_URL unset:

::error title=Missing env key::REDIS_URL is listed in .env.example but is not set
::error title=Empty env key::JWT_SECRET is set but empty
EnvGate Lite: 1 missing, 1 empty (of 3).
Full EnvGate CLI (placeholders, extra keys, secret shapes, JSON): https://ess2292.github.io/envgate/
exit=1

With fail-on-empty left at its default ("false"), the same environment reported only REDIS_URL (1 missing, 0 empty); the empty JWT_SECRET passed. JWT_SECRET set to spaces was reported as empty with fail-on-empty: "true". With all three keys non-empty it printed EnvGate Lite: OK, 3 key(s) present. and returned 0. As with the conftest.py check, decide what should happen on fork pull requests, where secret-backed keys are always empty.

Keep .env.example in step with the workflow

Every fix above only checks keys that .env.example (or the settings model) lists. The workflow passes SENTRY_DSN, which the example file does not mention. The EnvGate CLI reads workflow env: blocks and reports that. Scan mode in the sample repo (no .env):

What EnvGate does not catch

  • It does not read Python code. Adding SMTP_HOST = os.environ["SMTP_HOST"] to app/config.py changed nothing in envgate check: no line mentioned SMTP_HOST and it still exited 0. Fields on a pydantic-settings model are invisible too. Only keys in the example file (and, for the CLI, in workflow env: blocks and Compose files) are checked.
  • The CLI’s --from-env counts an empty value as present. In the run above, JWT_SECRET="" passed. For empty secrets and fork pull requests, use Lite with fail-on-empty: "true" or the conftest.py check.
  • Scan mode with no .env checks no values. In a clean checkout, plain envgate check printed PASS — no violations. with nothing set, because a missing sibling .env is not an error in scan mode. It still reported the workflow key missing from .env.example.
  • It does not know how your project loads env. Neither tool knows whether you call load_dotenv, use pytest-dotenv, or rely on pydantic-settings. With a complete local .env, envgate check passed (env: .env) even though plain pytest without a loader still raised KeyError.
  • Lite reads the job environment, not .env, unless you pass env-file. With a complete .env in the directory and nothing in the environment, Lite reported all three keys missing (3 missing, 0 empty (of 3)). That is correct for CI, but it means Lite is not a local check of your .env file.
  • Some workflow file names are skipped. EnvGate 0.2.1 does not read env: blocks from workflows it treats as tooling (for example build.yml, lock.yml, or names containing release or publish). The sample used test.yml, which is read.
  • Present is not correct. A non-empty DATABASE_URL that points at the wrong database passes every check on this page, and no type checks are done (pydantic-settings is the right tool for that).
