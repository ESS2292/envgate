Next.js NEXT_PUBLIC_ variable undefined in a Docker or CI build: fail the build instead

next build copies the value of every process.env.NEXT_PUBLIC_* reference into the browser JavaScript. If the key is unset or empty at that moment — inside docker build or a CI step — the build still succeeds and the browser gets undefined or "". Setting the variable later with docker run -e does not change it.

The usual report: the app works with next dev, but in the container the browser logs undefined for process.env.NEXT_PUBLIC_API_URL, even though docker run -e NEXT_PUBLIC_API_URL=... was set and printenv inside the container shows it.

Everything below was run on November 23, 2026 with Next.js 16.4.6 (Turbopack, the bundler next build used by default here), React 19.3.1, Node.js 24.22.1 on the host and 24.22.3 in node:24-slim, npm 11.21.1, Docker Engine 26.1.5 with buildx 0.13.1 (BuildKit) on Debian 13, EnvGate 0.2.1, and the EnvGate Lite Action source at tag v1 (v1.1.0, commit aaae8a9). Browser output comes from headless Google Chrome loading the page served by next start. Output is pasted as printed, except where a line says it was trimmed.

Why the value is undefined

The Next.js environment variables guide describes the mechanism:

  • Only prefixed keys reach the browser. “Non-NEXT_PUBLIC_ environment variables are only available in the Node.js environment, meaning they aren’t accessible to the browser.”
  • Values are inlined at build time. Next.js replaces references “with the value from the environment in which you run next build.” The docs add: “if you … build and deploy a single Docker image to multiple environments, all NEXT_PUBLIC_ variables will be frozen with the value evaluated at build time.”
  • Dynamic lookups are not inlined. process.env[varName] and const env = process.env; env.NEXT_PUBLIC_X are not replaced.
  • Sources: process.env first, then .env.$(NODE_ENV).local, .env.local, .env.$(NODE_ENV), .env. next build runs with NODE_ENV=production.

In CI and in a Docker build the .env* files are usually not there (gitignored, or excluded by .dockerignore), so the only source left is the build environment.

Reproducing it

A minimal App Router app with one client component, app/Client.js:

'use client'
export default function Client() {
  console.log('marker-api', process.env.NEXT_PUBLIC_API_URL)
  console.log('marker-key', process.env.API_KEY)
  return <p>client</p>
}

Each build ran npx next build; the statement was then pulled out of .next/static/chunks/. All builds exited 0.

# nothing set, no .env files (a clean CI checkout)
console.log("marker-api",o.default.env.NEXT_PUBLIC_API_URL)
console.log("marker-key",o.default.env.API_KEY)

# NEXT_PUBLIC_API_URL=https://api.example.com API_KEY=abc123 npx next build
console.log("marker-api","https://api.example.com")
console.log("marker-key",o.default.env.API_KEY)

# NEXT_PUBLIC_API_URL= npx next build      (set, but empty)
console.log("marker-api","")
console.log("marker-key",o.default.env.API_KEY)

When the key is unset, this Turbopack build leaves a lookup on the browser’s process shim instead of a literal. That lookup does not read the server’s environment. Serving the “nothing set” build with values supplied only at start time, the browser console showed:

# built with nothing; started with
#   NEXT_PUBLIC_API_URL=https://runtime.example.com API_KEY=abc123 next start
marker-api undefined
marker-key undefined

# built with NEXT_PUBLIC_API_URL=https://api.example.com; started with nothing
marker-api https://api.example.com
marker-key undefined

# built with NEXT_PUBLIC_API_URL= (empty)
marker-api 
marker-key undefined

API_KEY never reached the browser, set or not. That is the intended protection for server-only secrets.

The same thing inside Docker

A typical single-stage Dockerfile that builds inside the image:

FROM node:24-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npx next build
EXPOSE 3000
CMD ["node", "node_modules/next/dist/bin/next", "start", "-p", "3000"]

Four ways it went wrong in testing (the first three builds exited 0):

  • docker run -e is too late. docker run -e NEXT_PUBLIC_API_URL=https://runtime.example.com on this image: the browser logged marker-api undefined.
  • --build-arg without an ARG line does nothing. docker build --build-arg NEXT_PUBLIC_API_URL=https://api.example.com on the Dockerfile above still produced undefined. BuildKit printed no warning. Only the deprecated legacy builder (DOCKER_BUILDKIT=0) said so: 
    [Warning] One or more build-args [NEXT_PUBLIC_API_URL] were not consumed
  • ARG declared but no value passed becomes an empty string. With ARG NEXT_PUBLIC_API_URL and ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL before the build, but no --build-arg, the browser logged an empty marker-api, not undefined.
  • .dockerignore drops .env.production. With .env* in .dockerignore, the build inside the image printed no - Environments: .env.production line, and the next.config.mjs guard from Fix 1 stopped it with Missing build-time env: NEXT_PUBLIC_API_URL, NEXT_PUBLIC_SENTRY_DSN (without the guard, that build would have inlined nothing). Without that ignore line, the build printed - Environments: .env.production and used it. Committing real values in .env.production is a separate decision; only do it for public values.

One more case: an ARG declared before FROM is not visible inside the stage. The Dockerfile reference covers scope; in testing, ARG NEXT_PUBLIC_API_URL placed above FROM node:24-slim with --build-arg passed still left the variable empty in the stage (the guard below caught it).

Fix 1: declare the build args and fail the build from next.config.mjs

Pass every client key into the build stage:

FROM node:24-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
ARG NEXT_PUBLIC_API_URL
ARG NEXT_PUBLIC_SENTRY_DSN
ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL \
    NEXT_PUBLIC_SENTRY_DSN=$NEXT_PUBLIC_SENTRY_DSN
RUN npx next build
EXPOSE 3000
CMD ["node", "node_modules/next/dist/bin/next", "start", "-p", "3000"]

Then make a blank value a build failure. next.config.mjs can export a function that receives the phase; this throws only for next build:

import { PHASE_PRODUCTION_BUILD } from 'next/constants.js'

// Client keys that get inlined at build time and must not be blank.
const required = ['NEXT_PUBLIC_API_URL', 'NEXT_PUBLIC_SENTRY_DSN']

export default (phase) => {
  if (phase === PHASE_PRODUCTION_BUILD) {
    const missing = required.filter((k) => !process.env[k]?.trim())
    if (missing.length) {
      throw new Error(`Missing build-time env: ${missing.join(', ')}`)
    }
  }
  return {}
}

Results:

$ NEXT_PUBLIC_SENTRY_DSN= npx next build
▲ Next.js 16.4.6 (Turbopack)
⨯ Failed to load next.config.mjs, see more info here https://nextjs.org/docs/messages/next-config-error

> Build error occurred
Error: Missing build-time env: NEXT_PUBLIC_API_URL, NEXT_PUBLIC_SENTRY_DSN
    at default (next.config.mjs:10:13)
exit=1

$ docker build --progress=plain --build-arg NEXT_PUBLIC_API_URL=https://api.example.com -t web .
(earlier steps trimmed)
#10 0.686 Error: Missing build-time env: NEXT_PUBLIC_SENTRY_DSN
#10 0.686     at default (next.config.mjs:10:13)
#10 ERROR: process "/bin/sh -c npx next build" did not complete successfully: exit code: 1
(snippet trimmed)
ERROR: failed to solve: process "/bin/sh -c npx next build" did not complete successfully: exit code: 1

With both build args set, docker build exited 0. With both keys in .env.production and nothing in the shell, the local build printed - Environments: .env.production before running the config and passed, so the guard sees values from .env* files as well. next dev still started and served the page with nothing set, because the check only runs in the production build phase. The same guard caught the .dockerignore and ARG-before-FROM cases above.

If the values really must change per environment without rebuilding, the docs’ answer is to read them on the server during dynamic rendering (after await connection()) and pass them to the client yourself, not to use NEXT_PUBLIC_.

Where the empty string comes from in GitHub Actions

A common workflow hands values to docker build by name. --build-arg NAME with no =value takes the value from the step’s environment; in testing, an empty environment value went through as empty and the guard failed the build with Missing build-time env: NEXT_PUBLIC_SENTRY_DSN.

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      NEXT_PUBLIC_API_URL: ${{ vars.NEXT_PUBLIC_API_URL }}
      NEXT_PUBLIC_SENTRY_DSN: ${{ secrets.NEXT_PUBLIC_SENTRY_DSN }}
    steps:
      - uses: actions/checkout@v5
      - run: docker build --build-arg NEXT_PUBLIC_API_URL --build-arg NEXT_PUBLIC_SENTRY_DSN -t web .

GitHub documents that a secret that “has not been set” makes the expression return an empty string (Using secrets); configuration variables behave the same (Store information in variables). Except for GITHUB_TOKEN, “secrets are not passed to the runner when a workflow is triggered from a forked repository,” and Dependabot-triggered runs do not get them either. Each of those builds gets "".

Two cautions. A NEXT_PUBLIC_ value ends up in public JavaScript, so storing it as a GitHub secret only hides it from logs. And the Dockerfile reference warns: “It isn’t recommended to use build arguments for passing secrets such as user credentials, API tokens, etc. Build arguments are visible in the docker history command and in max mode provenance attestations.” Keep real secrets out of NEXT_PUBLIC_ keys and out of build args.

Fix 2: check the job environment against .env.example before the build

If .env.example lists the client keys, the free EnvGate Lite GitHub Action can fail the job before docker build starts. Keep the values at job level so the check and the build see the same environment:

    steps:
      - uses: actions/checkout@v5
      - uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"
      - run: docker build --build-arg NEXT_PUBLIC_API_URL --build-arg NEXT_PUBLIC_SENTRY_DSN -t web .

Run through the action’s own run() entry point with .env.example listing NEXT_PUBLIC_API_URL and NEXT_PUBLIC_SENTRY_DSN:

::error title=Empty env key::NEXT_PUBLIC_SENTRY_DSN is set but empty

With both keys non-empty it printed EnvGate Lite: OK, 2 key(s) present. and returned 0. Without fail-on-empty: "true", the empty-secret case also printed OK, 2 key(s) present. and passed, so set it for build-time keys. If fork PRs should still build, leave secret-backed keys out of this check or skip the image build for forks.

Where EnvGate does not help

  • It does not read Dockerfiles or build args. Adding ARG NEXT_PUBLIC_FEATURE_FLAGS to the sample Dockerfile, with no matching .env.example entry, produced no finding. EnvGate 0.2.1 also does not read --build-arg flags in workflow run: lines or Compose build.args, and it cannot tell that an ARG is missing, declared above FROM, or never copied into ENV. The next.config.mjs guard covers those.
  • The CLI’s --from-env did not flag empty values. With NEXT_PUBLIC_SENTRY_DSN set to "", it printed PASS — no violations. and exited 0. For empty secrets and fork PRs, use Lite with fail-on-empty: "true" or the config guard.
  • It does not read your source code. It cannot tell that a client component uses process.env.API_KEY (always undefined in the browser) or a NEXT_PUBLIC_ key that is missing from .env.example, or that a dynamic process.env[name] lookup will never be inlined.
  • It does not know about build time vs run time. A key that is present in the container at docker run passes any check you run there, even though the browser bundle was frozen with undefined at build time. Run the check in the job that builds the image.
  • It does not see .dockerignore. A .env.production that exists in the repo passes a repo-level check even if .dockerignore keeps it out of the build context.
  • Present is not correct. A non-empty NEXT_PUBLIC_API_URL that points at the wrong host passes every check on this page.
