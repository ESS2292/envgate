Jest or Vitest: process.env variable undefined in CI (the .env file is not loaded)

Jest does not read .env at all, and Vitest only exposes VITE_-prefixed keys from it. Add a loader and tests pass locally, but in CI the .env file is gitignored, so the loader quietly loads nothing. Here is what each setup actually does, and how to make a missing or empty variable fail the run with a clear message.

The usual report: process.env.DATABASE_URL is undefined inside a test, or tests pass on a laptop and fail in GitHub Actions with a connection error that has nothing to do with the code under test.

Everything below was run on November 25, 2026 on Linux with Node.js 24.22.1, npm 11.21.1, Vitest 5.1.2 (vitest/5.1.2 linux-x64 node-v24.22.1, which installed Vite 8.3.8), Jest 30.5.2, dotenv 18.0.10, EnvGate 0.2.1, and the EnvGate Lite Action source at tag v1 (commit aaae8a9). No GitHub Actions runner was used; where this page describes runner behavior, it quotes GitHub’s docs. Output is pasted as printed (ANSI colors stripped), except where a line says it was trimmed.

What each test runner does with .env

The sample project has this .env next to package.json, and no config file:

DATABASE_URL=postgres://app@localhost/app
VITE_API_URL=http://localhost:3000

Vitest 5.1.2. A test that logs both keys from process.env and import.meta.env:

$ npx vitest run
stdout | test/env.test.js > env
process.env.DATABASE_URL = undefined
process.env.VITE_API_URL = "http://localhost:3000"
import.meta.env.DATABASE_URL = undefined
import.meta.env.VITE_API_URL = "http://localhost:3000"
MODE = test
(assertion output trimmed)
 Test Files  1 failed (1)
exit=1

Vitest runs in mode test and loaded the .env file, but only the VITE_ key reached the test, on both process.env and import.meta.env. A .env.test file behaved the same way: VITE_TEST_ONLY from it was loaded, an unprefixed key next to it was not. That matches the Vite env docs, where only prefixed keys are exposed; the Vitest config docs do not say this directly, so treat it as observed behavior for these versions.

Jest 30.5.2. The same .env, a test that logs the key:

$ npx jest
  console.log
    DATABASE_URL = undefined NODE_ENV = test
(assertion output trimmed)
Tests:       1 failed, 1 total
exit=1

Jest set NODE_ENV to test and did not read .env. Nothing in Jest loads it unless you add a loader.

The three common loaders, and what they do in CI

Each of these fixed the local run (the test passed with the .env above). Then the .env file was removed, which is what a clean CI checkout looks like when .env is in .gitignore:

LoaderLocal, .env presentCI, no .env
Vitest: test: { env: loadEnv(mode, process.cwd(), '') }passtests run with DATABASE_URL undefined; no warning
Jest or Vitest: setupFiles: ['dotenv/config']passtests run with DATABASE_URL undefined; no warning
node --env-file=.env node_modules/vitest/vitest.mjs run (and the same for Jest’s bin/jest.js)passNode exits 9 before any test runs: /usr/local/lib/nodejs/node: .env: not found
node --env-file-if-exists=.env …passtests run with DATABASE_URL undefined; no warning

The loadEnv(mode, process.cwd(), '') form comes from the Vite config docs (“Set the third parameter to '' to load all env regardless of the VITE_ prefix”, vitejs/vite docs/config/index.md at 86bf306), and Vitest’s test.env puts those values on process.env and import.meta.env during tests. The Node docs for v24.22.1 say of --env-file: “An error is thrown if the file does not exist.” That error is the only loud failure in the table, and it fails for the wrong reason: the job may set every variable correctly and still die because the file is missing.

So the loaders all work the same way: when .env is there they fill process.env, and when it is not they do nothing (or, with --env-file, fail on the file instead). In CI the values have to come from the job’s environment.

The empty-variable trap: an empty job variable beats .env

None of these loaders overwrite a variable that already exists, even when it is an empty string. The dotenv README (18.0.10) says: “By default, we will never modify any environment variables that have already been set.” The Vite docs say variables that already exist when Vite runs “have the highest priority and will not be overwritten by .env files.” Node’s --env-file docs: “If the same variable is defined in the environment and in the file, the value from the environment takes precedence.”

Tested with DATABASE_URL=postgres://app@localhost/app in .env:

# Jest with setupFiles: ['dotenv/config']
$ DATABASE_URL= npx jest
    DATABASE_URL = "" NODE_ENV = test
Tests:       1 failed, 1 total

# Vitest with test.env = loadEnv(mode, process.cwd(), '')
$ DATABASE_URL= npx vitest run
process.env.DATABASE_URL = ""
 Test Files  1 failed (1)

This matters in GitHub Actions because of how secrets expand. GitHub’s secrets docs (github/docs at 73e24e6): “If a secret has not been set, the return value of an expression referencing the secret … will be an empty string,” and “With the exception of GITHUB_TOKEN, secrets are not passed to the runner when a workflow is triggered from a forked repository.” A line like DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }} therefore sets DATABASE_URL to "" on fork pull requests or when the secret is misnamed, and that empty value wins over any committed .env.test. (The runner behavior is quoted from the docs; the precedence was tested locally as shown.)

Fix 1: a setup file that fails on missing or empty keys

Keep the loader for local runs, and add a second setup file that reads .env.example and throws if any listed key is unset or blank. Setup files run in order, so the check sees whatever the loader added.

Vitest (test/require-env.js, project with "type": "module"):

// Fail the run if a key listed in .env.example is unset or blank.
import { readFileSync } from 'node:fs'

const keys = readFileSync('.env.example', 'utf8')
  .split(/\r?\n/)
  .map((l) => l.trim())
  .filter((l) => l && !l.startsWith('#'))
  .map((l) => l.replace(/^export\s+/, '').split('=')[0].trim())

const missing = keys.filter((k) => !process.env[k] || !process.env[k].trim())
if (missing.length) {
  throw new Error(`Missing test env: ${missing.join(', ')} (listed in .env.example)`)
}
// vitest.config.js
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    setupFiles: ['dotenv/config', './test/require-env.js'],
  },
})

For Jest, the same file as CommonJS (test/require-env.cjs, with const { readFileSync } = require('node:fs') as the only change) and:

// jest.config.js
module.exports = {
  setupFiles: ['dotenv/config', '<rootDir>/test/require-env.cjs'],
}

.env.example lists DATABASE_URL, JWT_SECRET, and REDIS_URL. Results, with no .env, DATABASE_URL set, JWT_SECRET set to an empty string, and REDIS_URL unset:

$ npx jest
FAIL __tests__/env.test.js
  ● Test suite failed to run

    Missing test env: JWT_SECRET, REDIS_URL (listed in .env.example)

(code frame trimmed)
      at Object.<anonymous> (test/require-env.cjs:12:9)

Test Suites: 1 failed, 1 total
Tests:       0 total
exit=1

$ npx vitest run
 FAIL  test/env.test.js [ test/env.test.js ]
Error: Missing test env: JWT_SECRET, REDIS_URL (listed in .env.example)
 ❯ test/require-env.js:12:9
(code frame trimmed)
 Test Files  1 failed (1)
      Tests  no tests
exit=1

Other cases, same for both runners: all three keys set in the environment, exit 0; a complete local .env and nothing in the shell, exit 0; a complete .env plus JWT_SECRET= in the shell, exit 1 with Missing test env: JWT_SECRET (the empty-variable trap, now caught). Two limits: setup files run once per test file, so a suite with 40 files prints the error 40 times, and the simple parser above does not handle quoted keys or KEY = value with odd spacing beyond trimming.

Fix 2: check the job environment before the tests start

In GitHub Actions, put the values at job level so the check and the test step see the same environment, then run the free EnvGate Lite Action before npm ci:

jobs:
  test:
    runs-on: ubuntu-latest
    env:
      DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}
      JWT_SECRET: ${{ secrets.JWT_SECRET }}
      REDIS_URL: ${{ vars.REDIS_URL }}
      MAILER_API_KEY: ${{ secrets.MAILER_API_KEY }}
    steps:
      - uses: actions/checkout@v5
      - uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"
      - uses: actions/setup-node@v5
        with:
          node-version: 24
      - run: npm ci
      - run: npx jest

Run locally through the action’s own run() entry point at v1, with the action inputs passed as INPUT_* variables the way the runner does, DATABASE_URL set, JWT_SECRET empty, and REDIS_URL unset:

::error title=Missing env key::REDIS_URL is listed in .env.example but is not set
::error title=Empty env key::JWT_SECRET is set but empty
EnvGate Lite: 1 missing, 1 empty (of 3).
Full EnvGate CLI (placeholders, extra keys, secret shapes, JSON): https://ess2292.github.io/envgate/
exit=1

With fail-on-empty left at its default ("false"), the same environment reported only REDIS_URL (1 missing, 0 empty); the empty JWT_SECRET passed. With all three keys non-empty it printed EnvGate Lite: OK, 3 key(s) present. and returned 0. As with the setup file, decide what should happen on fork pull requests, where secret-backed keys are always empty.

Keep .env.example in step with the workflow

Both fixes only check keys that .env.example lists. The workflow above passes MAILER_API_KEY, which the example file does not mention. The EnvGate CLI reads workflow env: blocks and reports that. Scan mode in the sample repo (no .env):

$ envgate check
EnvGate check
  examples: .env.example
  env:      (none)
  workflows: .github/workflows/test.yml

Warnings (1):
  [actions_undocumented] MAILER_API_KEY: GitHub Actions env "MAILER_API_KEY" in .github/workflows/test.yml is passed from secrets or vars, but is not listed in any example file.

PASS — no violations.
(1 warning)
exit=0

To check the job environment with the CLI, use pair mode with an empty file and --from-env. Same environment as the Lite run (JWT_SECRET empty, REDIS_URL unset):

$ envgate check --env /dev/null --example .env.example --from-env
EnvGate check
  example: .env.example
  env:     ../../../dev/null

Errors (1):
  [missing_key] REDIS_URL: Missing key "REDIS_URL" (required by .env.example)

Warnings (1):
  [actions_undocumented] MAILER_API_KEY: GitHub Actions env "MAILER_API_KEY" in .github/workflows/test.yml is passed from secrets or vars, but is not listed in any example file.

FAIL — 1 error, 1 warning.
exit=1

Note what it did not report: the empty JWT_SECRET. See below.

What EnvGate does not catch

  • The CLI’s --from-env counts an empty value as present. In the run above, JWT_SECRET="" passed. For empty secrets and fork pull requests, use Lite with fail-on-empty: "true" or the setup-file check.
  • Scan mode with no .env checks no values. In a clean checkout, plain envgate check printed PASS — no violations. with nothing set, because a missing sibling .env is not an error in scan mode. It still reported the workflow key missing from .env.example.
  • It does not know how your test runner loads env. Neither the CLI nor Lite knows that Jest ignores .env, that Vitest only passes VITE_ keys, or that dotenv/config is missing from setupFiles. With a complete local .env, envgate check passed (env: .env) even though Jest without a loader would still see undefined.
  • Lite reads the job environment, not .env, unless you pass env-file. With a complete .env in the directory and nothing in the environment, Lite reported all three keys missing. That is correct for CI, but it means Lite is not a local check of your .env file.
  • It does not read test code. A test that uses process.env.SOME_KEY not listed in .env.example is invisible to both tools. Only keys in the example file (and, for the CLI, in workflow env: blocks and Compose files) are checked.
  • Some workflow file names are skipped. EnvGate 0.2.1 does not read env: blocks from workflows it treats as tooling (for example build.yml, lock.yml, or names containing release or publish). The sample used test.yml, which is read.
  • Present is not correct. A non-empty DATABASE_URL that points at the wrong database passes every check on this page.
