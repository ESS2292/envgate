Vite import.meta.env variable undefined in CI: fail the build instead of shipping undefined

Vite replaces import.meta.env.* at build time. If a key is unprefixed, unset, or empty when vite build runs in CI, the build still succeeds and the bundle ships undefined or "". Here is why, and how to make it a failing step.

The usual report: the app works with vite dev on a laptop, but the deployed build calls undefined/api/users, or console.log(import.meta.env.API_URL) prints undefined. Nothing failed in CI.

Everything below was run on November 21, 2026 against a small sample project with Vite 8.3.8 (vite/8.3.8 linux-x64 node-v24.22.1), npm 11.21.1, EnvGate 0.2.1, and the EnvGate Lite Action source at tag v1 (v1.1.0). Output is pasted as printed, except where a line says it was trimmed.

Why the value is undefined

The Vite env docs state three rules that explain nearly every case:

  • Only prefixed keys reach client code. “Variables prefixed with VITE_ will be exposed in client-side source code after Vite bundling.” Their own example: import.meta.env.DB_PASSWORD is undefined. The prefix can be changed with envPrefix.
  • Values are inlined at build time. import.meta.env constants are “statically replaced at build time.” Whatever the CI job has when vite build runs is baked into the JavaScript. Setting the variable later on the server that hosts the static files changes nothing.
  • Sources: .env, .env.local, .env.[mode], .env.[mode].local, and environment variables that already exist when Vite starts, which “have the highest priority and will not be overwritten by .env files.” vite build runs in production mode unless you pass --mode.

In CI the .env file is normally not there (it is gitignored), so the only source left is the job’s environment.

Reproducing it

src/main.js:

console.log('api', import.meta.env.VITE_API_URL)
console.log('key', import.meta.env.API_KEY)
console.log('mode', import.meta.env.MODE)

Each build below ran npx vite build, then the matching statement was pulled out of the minified file in dist/assets/. All builds exited 0.

# nothing set, no .env (a clean CI checkout)
console.log(`api`,void 0),console.log(`key`,void 0),console.log(`mode`,`production`)

# VITE_API_URL=https://api.example.com API_KEY=abc123 npx vite build
console.log(`api`,`https://api.example.com`),console.log(`key`,void 0),console.log(`mode`,`production`)

# VITE_API_URL= npx vite build      (set, but empty)
console.log(`api`,``),console.log(`key`,void 0),console.log(`mode`,`production`)

# .env.production has VITE_API_URL=https://prod.example.com
#   npx vite build
console.log(`api`,`https://prod.example.com`),console.log(`key`,void 0),console.log(`mode`,`production`)
#   npx vite build --mode staging   (no .env.staging)
console.log(`api`,void 0),console.log(`key`,void 0),console.log(`mode`,`staging`)

What this shows:

  • API_KEY was void 0 (undefined) in every build, even when it was set. Unprefixed keys never reach client code, which is what you want for real secrets.
  • An unset VITE_ key becomes void 0; a set-but-empty one becomes ``. Neither fails the build.
  • --mode staging does not read .env.production. A pipeline that builds with a custom mode needs a .env.staging or the variables in the job environment.

With envPrefix: ['VITE_', 'APP_'] in vite.config.js, APP_API_URL=https://app.example.com was inlined as `https://app.example.com` and API_KEY stayed void 0. Setting envPrefix: '' stopped the build:

error during build:
Error: envPrefix option contains value '', which could lead unexpected exposure of sensitive information.

Where the empty string comes from in GitHub Actions

A typical workflow passes the values on the build step:

      - run: npm run build
        env:
          VITE_API_URL: ${{ vars.VITE_API_URL }}
          VITE_SENTRY_DSN: ${{ secrets.VITE_SENTRY_DSN }}

GitHub documents that a secret that “has not been set” makes the expression return an empty string (Using secrets), and the same for configuration variables (Store information in variables). The same page notes that, except for GITHUB_TOKEN, “secrets are not passed to the runner when a workflow is triggered from a forked repository,” and that secrets are not available to Dependabot-triggered workflows. In all of those cases the variable is set to an empty string, so Vite inlines "", as in the third build above.

Remember that anything with the VITE_ prefix ends up in public JavaScript. Storing it as a GitHub secret masks it in logs but does not make it private once it is in the bundle; Vite’s docs say VITE_* variables “should not contain sensitive information such as API keys.”

Fix 1: fail the build from vite.config.js

Vite exports loadEnv, which reads the same .env files for a given mode. In this test it also picked up prefixed keys from the shell environment, so it saw the same values the build would inline. This config throws during vite build when a required key is unset or blank, and leaves vite dev alone:

import { defineConfig, loadEnv } from 'vite'

// Keys the client bundle cannot work without.
const required = ['VITE_API_URL', 'VITE_SENTRY_DSN']

export default defineConfig(({ command, mode }) => {
  if (command === 'build') {
    const env = loadEnv(mode, process.cwd(), 'VITE_')
    const missing = required.filter((k) => !env[k] || !env[k].trim())
    if (missing.length) {
      throw new Error(`Missing build-time env: ${missing.join(', ')} (mode: ${mode})`)
    }
  }
  return {}
})

Results:

$ VITE_SENTRY_DSN= npx vite build
failed to load config from /tmp/vdemo/vite.config.js
error during build:
Error: Missing build-time env: VITE_API_URL, VITE_SENTRY_DSN (mode: production)
(stack trace trimmed)
exit=1

$ VITE_API_URL=https://api.example.com VITE_SENTRY_DSN=https://abc@o1.ingest.sentry.io/1 npx vite build
exit=0

# both keys in .env.production, nothing in the shell
$ npx vite build
exit=0
$ npx vite build --mode staging
Error: Missing build-time env: VITE_API_URL, VITE_SENTRY_DSN (mode: staging)

npx vite (the dev server) still started with nothing set, because the check only runs for command === 'build'. Pick the required list deliberately: on pull requests from forks, secrets are empty, so this check fails those builds. If that is not what you want, skip the build step for forks or keep secret-backed keys out of required.

Fix 2: catch unprefixed keys in source

The guard above checks values. It does not catch import.meta.env.API_KEY in code, which is undefined no matter what CI sets. A plain grep step catches that (tested with GNU grep 3.11 and bash 5.2; adjust the prefix list if you use envPrefix):

      - name: import.meta.env keys must use the VITE_ prefix
        shell: bash
        run: |
          bad=$(grep -rnoE 'import\.meta\.env\.[A-Za-z_][A-Za-z0-9_]*' src \
            | grep -vE 'import\.meta\.env\.(VITE_[A-Za-z0-9_]*|MODE|BASE_URL|PROD|DEV|SSR)$' || true)
          if [ -n "$bad" ]; then
            echo "::error::import.meta.env keys without the VITE_ prefix are undefined in the client bundle:"
            echo "$bad"
            exit 1
          fi
          echo "OK: every import.meta.env key is VITE_-prefixed or built in"

Against the sample src/main.js:

::error::import.meta.env keys without the VITE_ prefix are undefined in the client bundle:
src/main.js:2:import.meta.env.API_KEY
exit=1

After deleting that line it printed OK: every import.meta.env key is VITE_-prefixed or built in and exited 0. It is a text match: destructuring (const { API_KEY } = import.meta.env) and dynamic access (import.meta.env[name]) are not caught.

Fix 3: check the job environment against .env.example

If .env.example lists the VITE_ keys, the free EnvGate Lite GitHub Action can fail the job before the build starts. Put the values at job level so the check and the build see the same environment:

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      VITE_API_URL: ${{ vars.VITE_API_URL }}
      VITE_SENTRY_DSN: ${{ secrets.VITE_SENTRY_DSN }}
      VITE_ANALYTICS_ID: ${{ vars.VITE_ANALYTICS_ID }}
    steps:
      - uses: actions/checkout@v5
      - uses: ESS2292/envgate-action@v1
        with:
          example: .env.example
          fail-on-empty: "true"
      - uses: actions/setup-node@v5
        with:
          node-version: 24
      - run: npm ci
      - run: npm run build

Run through the action’s own run() entry point with .env.example listing all three keys, VITE_API_URL set, VITE_ANALYTICS_ID set to an empty string (what an unset variable or secret expands to), and VITE_SENTRY_DSN absent:

::error title=Missing env key::VITE_SENTRY_DSN is listed in .env.example but is not set
::error title=Empty env key::VITE_ANALYTICS_ID is set but empty
EnvGate Lite: 1 missing, 1 empty (of 3).
Full EnvGate CLI (placeholders, extra keys, secret shapes, JSON): https://ess2292.github.io/envgate/
exit=1

With all three set to non-empty values it printed EnvGate Lite: OK, 3 key(s) present. and returned 0. Without fail-on-empty: "true", an empty value counts as present, and the empty-secret case passes.

Keep .env.example in step with the workflow

Lite only checks keys that are already in .env.example. The EnvGate CLI also reads GitHub Actions env: blocks and flags keys passed from secrets or vars that no example file lists. In the sample repo, .env.example listed VITE_API_URL and VITE_SENTRY_DSN, the local .env only had VITE_API_URL, and .github/workflows/ci.yml passed all three keys:

Where EnvGate does not help

  • It does not read your source code. Neither the CLI nor Lite knows that src/ uses import.meta.env.API_KEY or a VITE_ key that is missing from .env.example. Use the grep step or a typed ImportMetaEnv (Vite docs, “IntelliSense for TypeScript”) for that.
  • The CLI’s --from-env did not flag empty values. In the run above, VITE_ANALYTICS_ID was set to "" and the CLI counted it as present. For the empty-secret and fork cases, use Lite with fail-on-empty: "true" or the vite.config.js guard.
  • Scan mode with no .env checks no values. In a clean checkout, plain envgate check printed PASS — no violations. even with nothing set, because a missing sibling .env is not an error in scan mode. It still reports workflow keys missing from .env.example.
  • Some workflow file names are skipped. EnvGate 0.2.1 treats workflows named build.yml or lock.yml (or starting with build-, build_, build., and the same for lock), or containing words like release or publish, as tooling and does not read their env: blocks. When the sample workflow was named build.yml, the actions_undocumented warning did not appear; renamed to ci.yml, it did.
  • It does not know about --mode. It compares .env.example with the environment it is given. It cannot tell that vite build --mode staging will skip .env.production.
  • Present is not correct. A non-empty VITE_API_URL that points at the wrong host passes every check on this page.
